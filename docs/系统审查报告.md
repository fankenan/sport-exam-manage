# 体育成绩管理系统 — 系统审查报告

- 审查对象：`https://github.com/fankenan/sport-exam-manage`（分支 `master`，Vue 3 + Element Plus + Express + MySQL）
- 审查范围：前端全部 16 个页面 / 9 个看板组件 / 2 个 Pinia Store，后端全部 8 个路由 / 中间件 / 数据库初始化脚本
- 验证方式：静态代码走查 + 依赖安装 + `vue-tsc` 类型检查 + `vite build` 产物分析 + `camelToSnake` 键名注入实测
- 结论：**系统骨架合理、功能基本可用，但存在 1 个 SQL 注入、8 处越权访问、1 个"改一行重写全库"的性能陷阱。当前状态下不建议直接上线给多所学校使用。**

---

## 0. 一句话诊断

三件事解释了"数据加载慢"，而且比想象的严重：

1. **后端有一个全量读取接口 `GET /api/data/sync`，四张表 `SELECT *` 无 LIMIT**，前端在启动时、每次进导入页、每次进看板页、每次导出时都会调用它。
2. **前端每修改一条记录，就调用 `saveToStorage()`——先 `GET` 全库、再 `POST` 全库 upsert。** 在 5 万条数据规模下，删一行会推送 5 万行。这是卡顿的头号元凶。
3. **首屏打包 1.19 MB JS + 358 KB CSS**（全量 Element Plus + 全量图标，无 tree-shaking），看板页再叠加 541 KB echarts，导入页再叠加 424 KB xlsx。

## 1. 阻断级问题（P0，必须修完才能上线）

### 1.1 SQL 注入 — `PUT /api/data/:table/:id`

`server/routes/grades.js:539-546` 与 `server/routes/grades.js:404-409` 把请求体的 key 直接拼进 `SET` 子句，而 `server/utils.js:30-43` 的 `camelToSnake` **不做任何键名白名单/转义**。实测：

```
输入 {"total = 1, name": "x"}
输出 {"total = 1, name":"x"}   ← 原样透传
拼接结果：UPDATE grade_seven SET total = 1, name = ? WHERE id = ?
```

攻击者可通过构造键名注入任意 `SET` 子句内容（进而可读取任意表、篡改其他字段）。同一模式在 `PUT /api/data/duplicates/:id` 复现。

**修复**：为每张表定义列白名单（`const ALLOWED_FIELDS = { grade_seven: [...], ... }`），只允许白名单内的列进入 SET 子句；并在 `camelToSnake` 之后增加 `/^[a-z_][a-z0-9_]*$/` 断言。

### 1.2 越权访问矩阵 — 学校账号可以碰到其他学校的数据

`requireAdmin` 中间件**只在 `admins.js` / `logs.js` / `schools.js` 三个文件里被用到**。`grades.js`、`reconsiderations.js`、`credentials.js`、`materials.js` 里的关键写操作和敏感读操作全部只有 `authMiddleware`：

| # | 接口 | 位置 | 越权后果 |
|---|---|---|---|
| 1 | `POST /api/data/clear` | `grades.js:347` | **学校账号可清空整库**（4 张表无条件 DELETE） |
| 2 | `POST /api/data/sync` | `grades.js:290` | **学校账号可全量覆盖所有学校的数据** |
| 3 | `GET /api/reconsiderations` | `reconsiderations.js:129` | 学校账号可读取**全部学校**的复核申请（含学生姓名、身份证号、成绩） |
| 4 | `PUT /api/reconsiderations/:id/approve` | `reconsiderations.js:195` | 学校账号可审批**其他学校**的申请 |
| 5 | `PUT /api/reconsiderations/:id/reject` | `reconsiderations.js:214` | 同上 |
| 6 | `GET /api/reconsiderations/check/:idCard` | `reconsiderations.js:146` | 学校账号可凭身份证号**枚举任意学生**在四张表中的全部记录 |
| 7 | `GET /api/materials/download/:id` | `materials.js:107` | 学校账号可下载**任意学校**的过程性材料 |
| 8 | `GET /api/credentials/download/:id` | `credentials.js:67` | 学校账号可下载**任意学生**的修改凭证（文件名里含身份证号，见 `credentials.js:86`） |
| 9 | `POST /api/credentials/upload` | `credentials.js:27` | 学校账号可覆盖**任意学生**的凭证记录 |
| 10 | `GET /api/data/duplicates` | `grades.js:393` | 学校账号可读取**其他学校**的重复数据（含身份证号等 PII） |

第 1、2 条尤其致命：这两个接口的破坏性是全库范围的，而 `admins` 表里默认就有一个 `admin/admin123` 的账号。

**修复**：在上述路由上补 `requireAdmin`（对 1、2、3、4、5 必加），对 6、7、8、9、10 补 `validateSchoolAccess(pool, req, record.school)` 归属校验。`clear` / `sync` 这类不可逆操作应额外要求二次确认口令。

### 1.3 生产环境自动创建弱口令管理员

`server/db.js:253-264` 无条件创建 `admin / admin123` 并把明文口令打印到启动日志：

```js
const hash = bcrypt.hashSync('admin123', 10)
...
console.log('[INIT] 默认管理员已创建: admin / admin123')
```

`server/index.js:62` 每次启动还会再打印一次。

**修复**：仅在 `NODE_ENV !== 'production'` 时创建；生产环境改为"首次启动生成随机一次性口令并写入文件"或强制走初始化向导。

### 1.4 CORS 全开 + 代理信任，可绕过登录限流

`server/index.js:11` `app.set('trust proxy', true)` + `server/index.js:20` `app.use(cors())`（任意来源、无凭证白名单）。

因为 token 存在 localStorage 而不是 Cookie，跨站 JS 拿不到 token，**实际被利用的路径是限流绕过**：`express-rate-limit` 在 `trust proxy: true` 下按 `X-Forwarded-For` 计数，攻击者每次伪造该头即可无限次尝试口令。

**修复**：`cors()` 改为白名单来源；`trust proxy` 改为 `app.set('trust proxy', 1)`（只信任第一跳）并确认部署在 Nginx 之后。

### 1.5 上传接口无文件类型校验

`materials.js:26`、`credentials.js:24`、`reconsiderations.js:26` 三处 multer 配置只限制了 `fileSize: 100MB`，**没有 `fileFilter`**，任意扩展名、任意内容都会落盘到 `server/uploads/`。100 MB × 多次上传是磁盘打满的现成路径。

**修复**：加 `fileFilter` 白名单（pdf/doc/docx/zip/jpg/png），落盘文件名改用随机 UUID（当前已是时间戳+随机数，尚可，但建议统一 UUID），并对总目录做容量上限。

### 1.6 密码修改后旧令牌仍然有效

`PUT /api/auth/password`（`auth.js:77-97`）只改密码哈希，不吊销已签发的 JWT。JWT 有效期 7 天（`.env.example:10`），改密码后原 token 在最长 7 天内仍可访问全部数据。

**修复**：引入 `token_version` 列，改密时自增，服务端校验时比对；或维护 token 黑名单。

### 1.7 `npm run build` 失败 — 类型检查 22 处报错

```
src/views/GradeImportView.vue(287,22): error TS7006: Parameter 'headers' implicitly has an 'any' type.
... (共 8 处 GradeImportView)
src/views/AdmissionGradesView.vue(418,34): error TS2339: Property 'total' does not exist on type '{}'.
... (共 14 处 AdmissionGradesView)
```

`package.json:8` 的 build 脚本是 `run-p type-check "build-only {@}" --`，type-check 失败即整体失败。（`vite build` 单独跑能过，产物 22.36s。）这意味着**任何 CI/CD 都无法构建本项目**。

**修复**：`AdmissionGradesView.vue:406` 的 Map 泛型应为 `Map<string, AdmissionData>` 而非 `{}`；`GradeImportView.vue` 的回调参数补类型标注。

## 2. 性能问题（"加载慢"的根因）

### 2.1 后端

| 问题 | 位置 | 影响 |
|---|---|---|
| **全量读取接口** | `grades.js:64-83` `GET /data/sync` | 4 张表 `SELECT *`，无 LIMIT、无分页。10 万条 ≈ 数百 MB JSON |
| **N+1 查询** | `grades.js:474-518` `/data/school-stats` | 每所学校 4 条 COUNT。50 所学校 = 200 次往返。应改为 2 条 `GROUP BY school` 聚合 |
| **逐行读写** | `grades.js:246-269` `POST /data/import` | 声明了 `BATCH = 500` 却没用上，实际是每行 1 次 SELECT + 1 次 UPDATE/INSERT。导入 5000 行 = 10000 次往返 |
| **逐行插入** | `grades.js:372-386` `POST /data/duplicates` | 每行一次 INSERT，无事务、无批量 |
| **相关子查询** | `middleware/rbac.js:11` | `school = (SELECT name FROM schools WHERE id = ?)` 每行求值一次 |
| **缺复合索引** | `db.js:273-285` | 只建了 `identity_id`/`graduation_year`/`school` 单列索引。实际最常用的过滤是 `school + graduation_year` 组合，应建复合索引 |
| **排序无索引** | `grades.js:157-165` | `ORDER BY name ASC` 无对应索引 → filesort |
| **模糊搜索全表扫** | `grades.js:167-172` | `LIKE '%kw%'` 无法走索引（可考虑 FULLTEXT 或 Elasticsearch，取决于数据量） |

### 2.2 前端

| 问题 | 位置 | 影响 |
|---|---|---|
| **改一条记录 = 重写全库** | `stores/grade.ts:351-369` `saveToStorage()` | 先 `GET` 全量再 `POST` 全量 upsert。删一行 = 推送 5 万行 |
| **启动即全量拉取** | `main.ts:31` `loadFromStorage()` | 进系统第一件事就是拉全库 |
| **重复全量拉取** | `GradeImportView.vue:535`、`MaterialUploadView.vue:316`、`DashboardView.vue:247` | 各页 `onMounted` 又拉一次；MaterialUpload 那次纯属多余（只要学校/年份列表） |
| **O(n²) 查重** | `GradeImportView.vue:482` → `stores/grade.ts:416-430` | 每行对全表做线性扫描。5000 行 × 5 万存量 = 2.5 亿次比较，**主线程冻结** |
| **O(n²) 查重** | `GradeImportView.vue:645` `targetList.find(...)` | 同上 |
| **O(n²) 导出预览** | `AdmissionGradesView.vue:577, 594` `rows.indexOf(row)` | 在 `for...of` 循环内调用，且跑了两遍 |
| **数组 includes** | `AdmissionGradesView.vue:449` `matchedIds.includes(a.id)` | 应改 `Set` |
| **看板客户端过滤全量** | `DashboardView.vue:244-251` | 服务端已支持 year/school 过滤（`grades.js:173-180`），前端却把全库拉下来再过滤 |
| **导出忽略筛选** | `GradeListView.vue:349`、`AdmissionGradesView.vue:686` | 用户筛了学校/年份，导出却是全库；且每次导出再触发一次全量拉取 |
| **静默截断** | `AdmissionGradesView.vue:388` `pageSize: 99999` | 服务端 `grades.js:146` 钳到 10000。**超过 1 万条候选时匹配结果被静默丢弃，界面照常显示"成功"** |
| **无虚拟滚动** | `grades.js:146` `pageSize` 上限 10000 | 一次渲染 1 万行 DOM，浏览器卡死 |

### 2.3 打包体积

`vite build` 产物分析：

```
assets/index-DPSze8qo.js        1,185.52 kB │ gzip: 381.94 kB   ← 首屏主包
assets/index-W8BFAfCB.css         357.90 kB │ gzip:  48.43 kB   ← 首屏样式
assets/DashboardView-*.js         541.37 kB │ gzip: 184.57 kB   ← echarts
assets/xlsx-*.js                  424.23 kB │ gzip: 141.75 kB   ← xlsx
assets/logo_run-*.png             362.23 kB                      ← 显示尺寸仅 28×28
```

根因：
- `main.ts:3` `app.use(ElementPlus)` — 全量引入，无法 tree-shake
- `main.ts:4-5` `import * as ElementPlusIconsVue` + 全量 `import 'element-plus/dist/index.css'`
- `main.ts:16-18` 循环注册全部图标
- `logo_run.png` 362 KB 却只显示 28×28

**预期收益**：改成 `unplugin-vue-components` 按需引入（项目已装好，只是 `main.ts` 没用）+ 替换 SVG logo + echarts 按需注册 + xlsx 动态加载，首屏可降到 **300 KB 以内（gzip ~100 KB）**。

## 4. 前端"高级感 / 质感"评估

### 现状
项目**并非**默认 Element Plus 裸用。`src/App.vue:10-68` 有一套完整的 Shadcn 风格 token 体系（语义色 + Element Plus 全套变量覆盖 + 组件级微调），`LoginView.vue`（动效网格背景、辉光光球、渐变顶边、背景模糊）是全站最精致的一屏，`LayoutView.vue` 的可折叠侧边栏也有设计。

### 但质感被以下问题稀释

**A. 两套配色并存** — token 主色是 slate-900 + blue-500，但：
- `LayoutView.vue:28-29, 376-377, 527, 590` 与 `LoginView.vue:162-189` 硬编码 `#00c6ff` 青 + `#8b5cf6` 紫
- `AdmissionGradesView.vue:86-87` 硬编码 `background: rgba(0,0,0,0.02)` / `color: #1d1d1f` —— 与 `--text-primary: #0f172a` **不是同一个色**，同样数据显示在不同页面文字颜色不同

**B. 外来设计词汇混入** — `AdmissionGradesView.vue:726-843` 整套 `.mac-card` / `.mac-select` / `.mac-btn` 类，radius 24px + 靛蓝阴影，与全局 `--radius-lg: 12px` 冲突，来源像是另一个项目的复制粘贴。

**C. 大量重复样式** — 同一段 `:deep(.el-button)/:deep(.el-table)/:deep(.el-pagination)` SCSS 在 `GradeListView.vue:375-394`、`GradeImportView.vue:806-825`、`GradeVerifyView.vue:448-467`、`MaterialUploadView.vue:333-352`、`SystemManageView.vue:499-512` 逐字重复 5 遍，**且 `App.vue:194-238` 已经全局做过同样的事**，纯属冗余。`GradeVerifyView.vue:441-446`、`MaterialUploadView.vue:326-331` 的 `:deep(.el-card)` 块更是死 CSS（两个模板里都没有 `el-card`）。

**D. 表头样式 9 处复制** — `:header-cell-style="{...}"` 这个 130 字符的内联对象在 9 个文件里各写一遍，而 `App.vue:201-210` 已用 `!important` 全局覆盖了它。

**E. 布局留白不一致** — `OperationLogsView.vue:241`、`SchoolManageView.vue:156`、`ChangePasswordView.vue:81` 用 `padding: 24px`，叠在 `LayoutView.vue:631` 的 `.main-content { padding: 24px }` 之上 = 48px；而其余页面用 `padding: 0` = 24px。同级页面视觉密度不一致。

**F. 表格边框不一致** — `AdmissionGradesView.vue:82` 缺 `border`；`GradeReviewView.vue:151` 缺 `header-cell-style`。

**G. 全局污染** — `LayoutView.vue:637-643` 用**非 scoped** 的 `<style>` 写了 `.el-table .cell { white-space: nowrap !important }`。该样式在 LayoutView 卸载后仍生效，且导致 `remark` 列（宽 80px）永远显示不全只能靠 tooltip。

**H. 状态覆盖不全**
| 项 | 覆盖 |
|---|---|
| `el-skeleton` | **全项目 0 处** |
| `el-empty` | 仅 2/16 页（`DashboardView.vue:42`、`MaterialUploadView.vue:85`） |
| `v-loading` | 缺 4 个视图：`GradeVerifyView`（3 张表）、`SystemManageView`、`MaterialUploadView`、`GradeImportView` 预览表 |
| 暗色模式 | 无 |
| 响应式 | 无（侧边栏固定 240px，无移动端/窄屏适配） |

**I. 死代码** — `components/GradeReviewTable.vue` 整个文件（90 行）**零引用**，是 `GradeListView` 的重复实现且自身分页双向绑定有 bug。

### 建议的质感方向
不动现有骨架的前提下，按这个顺序收敛即可：
1. 单一色源：把 `#00c6ff` / `#8b5cf6` / `#1d1d1f` 全部收敛进 token（建议定 `--brand-cyan` / `--brand-violet` / `--text-strong`），删掉 `.mac-*`
2. 抽 `styles/` 公共 SCSS（`_table.scss` / `_toolbar.scss` / `_page.scss`），删掉 5 份重复块
3. 统一页面容器：全局一个 `.page` 类解决留白差异
4. 补齐骨架屏 / 空态 / 加载态，形成一致的"加载 → 骨架 → 内容 → 空态"节奏
5. 补暗色模式（token 已就绪，只是多一套 `[data-theme=dark]` 值）
6. logo 换 SVG，362 KB → < 5 KB

## 5. 需求对照

### 需求 1 — 前端要有高级感、有质感
**当前：60 分。** 骨架（token 系统、精致登录页、设计化侧边栏）是对的，但被配色分裂、样式重复、留白不齐、状态覆盖缺失稀释。需要一次"收敛"而非"重做"。

### 需求 2 — 工作流程、页面布局、功能完善便利
**当前：55 分。** 缺的关键闭环：
- 缺"上报 → 审核 → 发布"状态机：`grade_seven/eight/nine` 有 `review_status`（`db.js:267-269`，默认 NULL）但**没有任何列表页面展示或流转它**；复核申请的 status 也不回写成绩表（见 3.4）
- 导入只有"计数"没有"差异预览"（新增/更新/冲突各多少条、各是哪几条）
- 看板"刷新"按钮只刷新数据不刷新筛选选项
- 成绩审核/复核/系统管理/学校管理 **4 个页面零分页**
- 导出忽略筛选条件
- 管理员无法自助改密

## 7. 架构建议（中期）

1. **成绩表增加 `school_id` 外键**，用 `JOIN schools` 代替字符串比较。理由：
   - 当前 `school VARCHAR(200)` 是自由文本，学校改名会**同时丢失该学校所有数据的关联**（`schools.name` 一改，`schoolFilter` 的子查询立刻匹配不到任何行）
   - 消除"一校两名 / 两校一名"的数据污染
   - 让 `(school_id, graduation_year)` 复合索引天然可用
2. **中招成绩匹配下沉到服务端**（一条 `JOIN` + `GROUP BY`），前端只渲染结果。当前在前端算，既慢又让客户端持有全量数据。
3. **统一 API 响应约定**：目前 `fail()` 永远返回 HTTP 200（`utils.js:9-13`），而 `authMiddleware` 返回 401、`rateLimit` 返回 429。同一套错误有三种传输方式，前端 `api/index.ts:14-34` 只能靠猜。建议全部用真实 HTTP 状态码。
4. **审计日志覆盖所有写操作**：`grades.js` 的 `clear`/`sync` targetTable 硬编码为 `grade_seven`；`duplicates` 的增删改完全没挂 `auditMiddleware`。

## B.8 「导入后合计校对不计算」的修复（2026-11-04 追加）

### 现象

导入成绩后，「合计校对」与「校对结果」两列为空，列表里所有记录都显示为 ❌ 异常。

### 根因（两个叠加的问题）

### 修复

**把规则的唯一定义放���服务端**，前端不再各算一套：

| 位置 | 改动 |
|---|---|
| `server/routes/grades.js` `applyDerivedFields()` | 新增：七/八年级统一算 `total_verify`（三项之和，保留 1 位小数）与 `verify_result`（一致=1，不一致=0）；未填合计时用三项之和补齐并视为通过 |

| `POST /data/sync` | 写入前调用 `applyDerivedFields()` |

| `server/routes/submissions.js` `validateRows()` | **移除**「合计≠三项之和」的硬校验错误 |
| `server/routes/submissions.js` `countMismatches()` | 新增：统计合计不符的条数，随预检结果返回 |
| `server/db.js` | 启动时回填历史数据：`total_verify IS NULL` 的行按服务端规则补算 |
| `src/stores/grade.ts` | 单条修改只提交原始字段，派生值由服务端算（消除两处规则） |

## B.9 表格换行与「管理员看不到上报」的修复（2026-11-04 追加）

### B.9.1 表格单元格换行

#### 现象

成绩列表页里「年级」显示成「七 / 年 / 级」三行、「合计」显示成「270. / 0」、「姓名」显示成「种子学 / 生0」。

#### 根因（三个叠加）

**① Element Plus 的 `.cell` 默认允许按字断行**

```css
.el-table .cell {
  text-overflow: ellipsis;
  white-space: normal;      /* ← 中文会按单字断行 */
  overflow-wrap: break-word;
  padding: 0 12px;
}
```

而 Element Plus 的样式是**按需分块加载**的（晚于本项目的 `App.vue`），
所以项目里同优先级的 `.el-table .cell { white-space: nowrap }` 被它覆盖掉了。
（顺带解释了一个细节：只有配了 `show-overflow-tooltip` 的列不换行 ——
因为 Element Plus 额外给它们加了 `.cell.el-tooltip { white-space: nowrap }`。）

**② 只配了 `width` 没配 `minWidth` 的列会塌缩**

`el-table` 的布局逻辑里有这么一段（`table-layout.mjs`）：

```js
} else {                       // 表格总宽 > 容器宽时走这里
  for (const column of columns) {
    column.realWidth = Number(column.minWidth)   // ← 只有 width 的列 = NaN
  }
}
```

`Number(undefined)` 是 `NaN`，列宽塌缩 → 内容换行。
全项目共 **101 处**列定义踩了这个坑。

**③ 双层内边距把可用宽度吃掉 24px**

`td` 有 `padding: 10px 12px`，里面的 `.cell` 又有 `padding: 0 12px`，
文字实际可用宽度 = 列宽 − 24（td）− 24（cell）− 2（边框），
比按内容算出来的列宽少了 26px，内容因此被省略号截断。

#### 修复

| 层面 | 改动 |
|---|---|
| 样式 | `.el-table .cell { white-space: nowrap !important; overflow-wrap: normal !important; word-break: keep-all !important; }` —— 用 `!important` 压过按需加载的 Element Plus 样式 |
| 样式 | `td` / `th` 的横向内边距清零（`padding: 10px 0`），横向留白交给 `.cell`，消除双层内边距 |
| 样式 | `.el-table { font-size: 13px !important }` —— 让字号令牌真正生效（Element Plus 自带 14px，同优先级但加载更晚） |
| 列定义 | 全部 **101 处**列补齐 `min-width`（脚本批量处理，`width` 与 `minWidth` 成对出现） |
| 列宽计算 | 新增 `src/utils/table.ts` + `src/composables/useAutoColumns.ts`：用 **canvas `measureText` 实测**文本宽度（不再靠估算），按「表头 + 当前页数据」算列宽，总宽超容器时按比例压缩 |
| 列宽计算 | 字号从真实 DOM 读取（`getComputedStyle`），保证测量与渲染一致；另加 3px 安全余量 |
| 覆盖范围 | 七/八/九年级成绩、中招体育成绩、上报审核三张主数据表已接入自动列宽；其余表格由全局 nowrap + min-width 兜底 |

#### 结果

浏览器实测（1440 / 1280 / 1100 / 900 四种视口，13 个页面）：

```
视口1440: 表格 1136/1136  横向滚动=无  换行单元格=0
视口1100: 表格 796/796    横向滚动=无  换行单元格=0
视口900:  表格 840/840    横向滚动=无  换行单元格=0
```

## B.10 时间显示、详情内容与表格铺满的修复（2026-11-04 追加）

### B.10.1 上报时间显示差 8 小时

**现象**：管理员端「提交时间」显示 08:49:09，实际是 16:49 传的。

**根因**：`snakeToCamel` 遇到 `Date` 会执行 `toISOString()` —— 那是 **UTC**。
MySQL 的 `default-time-zone='+08:00'`，库里 `CURRENT_TIMESTAMP` 存的是北京时间 16:49，
经 `toISOString()` 一转就变成 UTC 的 08:49，前端再原样显示 → **少 8 小时**。

**修复**：

| 位置 | 改动 |
|---|---|
| `server/db.js` | 连接池加 `dateStrings: true` —— DATETIME/TIMESTAMP 按字符串返回，**完全不做时区换算**，拿到的就是库里存的业务本地时间 |
| `server/utils.js` | `snakeToCamel` 的 Date 分支改用 `formatLocalDateTime()`（本地时间字符串），不再用 `toISOString()` |
| `src/utils/date.ts`（新增） | `formatDateTime()` 统一处理两种形态：`'YYYY-MM-DD HH:mm:ss'` 原样用；ISO/UTC 串转成本地时间 |
| 页面 | `SubmissionReviewView` / `GradeImportView` 的 `formatTime` 改用 `formatDateTime()`，不再各自写 `replace('T',' ')` |

### B.10.2 上报详情内容不对（七年级显示成九年级格式）

**现象**：抽屉里七年级上报的「数据明细」显示成「长跑 / 跳绳 / 球类 / 武术」，身份证号和年份都是空的。

**根因**：`snakeToCamel` 会**递归转换嵌套对象的键名**。
上报表的 `payload` 存的是 snake_case（`attendance_score`），
经 `snakeToCamel` 后变成 `attendanceScore`，而前端读的是 `p.attendance_score` → 全是 `undefined`
→ 模板里的 `v-if="row.attendanceScore !== undefined"` 判定失败，落到了九年级分支。

**修复**：前端按 camelCase 读取（并兼容旧的 snake_case）：
`p.attendanceScore ?? p.attendance_score`。同时给「成绩」列补了 `scoreText` 纯文本字段用于列宽测算。

### B.10.3 表格右侧留白 / 最后一列被挤出可视区

**修复**：

## B.12 九年级流程重构：学校只报名，教育局统一导入成绩（2026-11-05 追加）

### 背景

改造前，九年级和七、八年级走同一条路：学校导入成绩 → 管理员审核发布。实际业务里九年级成绩由教育局统一录入，学校只负责上报考生报名名单。

更关键的是**两个学生个人维度的项目**在成绩表里没有落脚点：

- **长跑分男女**——男生 1000 米、女生 800 米；
- **足（篮）球**——有人报足球、有人报篮球。

如果只让学校报成绩，这两个项目要么丢失，要么靠成绩列的顺序猜。所以必须让名单先进入系统，教育局导入成绩时再拿名单逐条核对。

### 新流程

```
学校：上传报名表 → 预检 → 提交
              ↓
教育局：报名审核（单条通过 / 批量通过 / 驳回）
              ↓  通过时写入两张成绩表的基本信息（成绩为空）
教育局：按身份证号导入成绩（逐条核对报名信息）
              ↓
两张成绩表同时落地成绩
```

### 数据模型：`grade_nine_registrations`

名单**独立成表**，不与成绩表混存，原因有三：

1. 成绩表按 `identity_id` upsert，名单需要保留「谁在什么时候报的、谁审的、原本报了什么」；
2. 用户明确要求**报名信息保留，供后续考务编排使用**；
3. 原始行以 `raw JSON` 整行落库，将来编排考场时列结构变了也不用再改表。

| 分组 | 字段 |
| --- | --- |
| 身份 | `school_id`、`school`、`name`、`gender`、`id_card`、`identity_id` |
| 学籍 | `registration_number`、`graduation_year`、`grade` |
| 项目 | `long_run_event`、`rope_skipping_event`、`long_jump_event`、`ball_event`、`martial_arts_event` |
| 审核 | `status`、`reject_reason`、`uploaded_by`、`reviewed_by`、`reviewed_at`、`scored_at` |
| 留存 | `remark`、`raw`(JSON)、`created_at`、`updated_at` |

状态机：

```
pending ──通过──→ approved ──导入成绩──→ scored
   └────驳回────→ rejected ──学校重传──→ pending
```

索引：`school`、`status`、`identity_id`、`graduation_year`、`registration_number`。

### 报名表模板

学校端「下载报名表模板」现在是**报名表**（不再是成绩表）：

```
学校 | 姓名 | 性别 | 身份证 | 报名序号 | 毕业年份 | 年级 | 项目1 | 项目2 | 项目3 | 项目4 | 项目5 | 备注
```

项目列按报名顺序自由填写，服务端用 `normalizeEvent()` 归一化：

| 输入 | 归一化 |
| --- | --- |
| 1000米 / 1000 / 男1000米 | `1000米` |
| 800米 / 800 / 女800米 | `800米` |
| 足球 / 足 | `足球` |
| 篮球 / 篮 | `篮球` |
| 跳绳、跳远、武术 | 同名 |

### 提交前的四道校对（`validateRegistrationRows`）

| # | 检查 | 不通过时的提示 |
| --- | --- | --- |
| 1 | 必填：姓名 / 身份证 / 报名序号 / 毕业年份 | `缺少报名序号` |
| 2 | 身份证格式与校验位 | `身份证号格式不正确` |
| 3 | 文件内身份证不可重复 | `与第 N 行身份证重复` |
| 4 | **性别 ↔ 身份证第 17 位** | `身份证号显示为女，但性别填的是男` |
| 5 | **性别 ↔ 长跑项目** | `男生应报 1000米，填的是「800米」` |
| 6 | 球类只能是足球或篮球 | `球类项目只能是「足球」或「篮球」` |
| 7 | 学校必须与账号所属学校一致 | `第 N 行学校「X」与账号学校「Y」不一致` |

备注含「病免 / 残免 / 弃考」的行跳过第 5 项（特殊考生不报长跑），但仍要求姓名/身份证/报名序号齐全。

### 审核通过写入了什么

通过的瞬间，在同一事务里往两张表各写一条（成绩列全部为 `NULL`，`review_status='published'`）：

| 目标表 | 学校 | 姓名 | 身份ID | 报名序号 | 毕业年份 | 年级 |
| --- | --- | --- | --- | --- | --- | --- |
| `grade_nine` | `school` | `name` | `identity_id` | `student_number` | `graduation_year` | `grade` |
| `admission` | `school` | `name` | `identity_id` | `registration_number` | `graduation_year` | `grade` |

`grade_nine` 历史上把报名序号存在 `student_number` 列，因此按既有列名写入，不新增列、不改历史数据。

### 成绩导入（`POST /api/registrations/import-scores`）

教育局上传的成绩表按**身份证号**与名单匹配，逐条校验：

| 检查 | 说明 |
| --- | --- |
| 名单中不存在 | `未在报名名单中` |
| 名单被驳回 | `报名已被驳回，不能导入成绩` |
| 性别 ↔ 长跑项目 | 男生必须 1000 米、女生必须 800 米 |
| 长跑项目与报名不一致 | `报名时为「1000米」，成绩文件填的是「800米」` |
| 球类项目与报名不一致 | `报名时是「足球」，成绩文件填的是「篮球」` |

任何一条不通过则**整批不写入**，接口返回 `err.errors`，前端在弹窗里以表格逐行展示错误。全部通过后两张表同时 upsert，名单状态置为 `scored`。

### 前端

| 角色 | 页面 | 形态 |
| --- | --- | --- |
| 学校 | `/grade-import` | 年级选「九年级（上报报名信息）」→ 上传报名表 → 预检 → 提交；下方是**我的报名记录**（姓名/性别/身份证/报名序号/长跑项目/球类项目/状态/驳回原因/提交时间） |
| 教育局 | `/registration-review` | 状态/学校/关键字筛选、多选批量通过、单条通过或驳回、**导入九年级成绩**、下载成绩模板 |

侧边栏「报名审核」带待审数量角标，与「上报审核」角标并列。

九年级成绩列表新增「报名序号」列（取自 `student_number`），方便与报名名单对照；中招体育成绩列表原本就有该列。

### 接口一览

| 方法 | 路径 | 权限 | 说明 |

### 实现

新增 `app_settings` 键值表（`setting_key` 主键 + `setting_value` + `updated_by` + `updated_at`），初始值：

```sql
INSERT IGNORE INTO app_settings (setting_key, setting_value, updated_by)
VALUES ('school_export_tables', 'grade_nine,admission', 'system')
```

接口：

| 方法 | 路径 | 权限 | 作用 |
| --- | --- | --- | --- |
| GET | `/api/settings/export-tables` | 登录即可 | 返回当前授权表列表，学校端据此决定显不显示导出按钮 |
| GET | `/api/settings` | 管理员 | 读取全部设置 |
| PUT | `/api/settings/school-export-tables` | 管理员 | 覆盖授权表列表 |

### 关键点：不是「藏按钮」，是服务端强校验

`POST /api/data/export` 在生成文件之前调用 `canExport(pool, req, table)`：

```js
async function canExport(pool, req, table) {
  if (!EXPORTABLE_TABLES.includes(table)) return false   // 白名单外的表一律拒绝
  if (!req.user) return false
  if (req.user.schoolId == null) return true             // 管理员不受限
  const allowed = await readSetting(pool)                // 学校：查实时设置
  return allowed.includes(table)
}
```

未授权直接 `403`，即使有人手搓请求也拿不到文件。实测：

```
export grade_nine: 200 application/vnd.openxmlformats-... 16065B
export admission : 403 application/json 91B
```

### 前端

- `/system-manage` 新增「学校端导出权限」区块：四张表各一个复选框 + 保存按钮，附一行说明「未勾选的成绩表，学校端的导出按钮会被隐藏（服务端导出接口同样会拦截，属于强制校验）」；
- 各成绩列表页在挂载时读 `/settings/export-tables`，学校账号未获授权则不渲染「导出Excel」按钮。

浏览器实测 A/B：只授权九年级时，学校端 `/grade-nine` 有「导出Excel」、`/admission-grades` 没有；接口层面同样是 200 / 403。

### 顺带修掉的一个旧问题

原来导出是**前端把当前页数据拼成 Excel**，只能导出当前页。现在改成 `POST /api/data/export` **服务端生成**：复用与列表相同的过滤条件，按 500 条一批拉全量（上限 20 万行），用 `xlsx` 在服务端生成后以 `Content-Disposition: attachment; filename*=UTF-8''...` 返回。导出的是**过滤后的全量数据**，不再是当前页。

## B.15 第二轮反馈的五处修正（2026-11-05 追加）

### 1. 备注与项目二选一：备注有内容 → 项目必须留空

原来只认关键词 `病免`，`残免`、`弃考` 会被当成「缺少长跑项目」拦下来。后来业务方把规则定得更彻底：

> **备注只要填了内容，五个项目列就必须全部留空；填了就直接在校验阶段筛出来。**

所以校验改成两条互斥分支：

```js
const remarkText = String(r.remark || '').trim()
const hasRemark = remarkText.length > 0

if (hasRemark) {
  // 特殊考生：病免 / 残免 / 弃考 / 其它，项目列必须全空
  if (filledProjects.length > 0) {
    errors.push({
      row: rowNum, field: 'remark',
      message: `备注填了「${remarkText}」，就不能再填项目（已填：${filledProjects.join('、')}），请把项目列全部清空`,
    })
  }
} else {
  // 正常考生：长跑必填，男 1000 米 / 女 800 米；球类只能是足球或篮球
}
```

它带来的三个变化：

- 不再依赖关键词表 —— 备注写「转学待定」也同样要求项目留空，判断标准只看「备注是否为空」；
- 报名模板新增第二个工作表 **「填写说明」**，把 6 条填报规则写清（解析只读第一个工作表，不影响导入）；
- 上传区提示补了一句「备注有内容时（病免/残免/弃考等）项目列必须留空」。

实测三种行混在一个文件里：

| 行 | 备注 | 项目 | 结果 |
| --- | --- | --- | --- |
| 正常甲 | 空 | 1000米 / 跳绳 / 跳远 / 足球 / 武术 | 通过 |
| 免考乙 | 病免 | 全空 | 通过 |
| 冲突丙 | 残免 | 1000米 / 跳绳 / 跳远 / 篮球 / 武术 | **拦下** |

报错原文：

```
备注填了「残免」，就不能再填项目（已填：长跑项目、跳绳项目、跳远项目、球类项目、武术项目），请把项目列全部清空
```

`test-registration.js` 相应增加 2 条断言（备注+项目被拦、非免考类备注填项目同样被拦），共 32 条。

### 2. 中招体育成绩页去掉「上传名单」

九年级报名审核通过时已经同时写入 `grade_nine` 与 `admission`，中招页再单独上传一份名单属于重复入口。删掉了「上传名单」「下载模板」两个按钮和整个三步式弹窗（选文件 → 预览 → 匹配写入），连带清理了 215 行死代码及 `RosterRow` 类型。「匹配成绩」（按身份证把七/八年级分数汇总进中招表）保留。

### 3. 九年级成绩的导入入口找不到了

**根因**：九年级成绩列表页（`/grade-nine`）根本没有导入按钮，只能从「成绩导入」页手动切换单选按钮；而成绩导入页默认停在「七/八年级」，看起来就像没有入口。

修法：

- `/grade-nine` 工具栏新增 **「导入九年级成绩」**（仅管理员可见），跳转 `/grade-import?mode=score9`；
- 成绩导入页读 `route.query.mode`，进入时直接落到九年级模式；
- 顺带把九年级成绩的导入**改成先预检、再确认**：原来点「校验并预览差异」其实会直接写库，没有任何确认步骤。

服务端 `POST /api/registrations/import-scores` 增加 `dryRun`：校验通过只返回可导入清单，不写库；`data._skipAudit` 让预检不进操作日志（`auditMiddleware` 也相应支持跳过）。

### 4. 列宽有的很挤、有的很宽，拖动后右侧留白

**三个原因**：

1. `absorb` 参数把全部剩余宽度塞给某一列（中招页是「报名序号」，成绩页是「备注」），所以出现了几百像素的空列；
2. 每列同时绑定了 `:width` 和 `:min-width`，Element Plus 把它们当**固定宽**，剩余空间无处可去；
3. 用户拖动某一列后，其余固定列不回收空间，最后一列被推走，右边空出一片。

**改法**：数据列只给 `min-width`（由内容实测得出），`width` 全部去掉。

- 内容放得下 → Element Plus 按 `min-width` 等比分配剩余空间，整表刚好铺满；
- 内容放不下 → 计算时先按比例压到容器内，仍然一页显示；
- 拖动某列 → 该列变成固定宽，其余列自动重分配，**右侧不再留白**。

实测（九年级 14 列，容器 1164px）：拖「姓名」从 65 → 175 后，学校 124→105、身份ID 173→153，总宽仍为 1162，`bodyScrollWidth === bodyClientWidth`。

顺带把写死的 `minWidth: '180'`（学校、身份ID）去掉 —— 它们让 6 个字的校名占了 189px，正是「有的很宽」的来源。

报名审核页原来 14 列硬编码宽度合计 1588px，容器只有 1164px，操作列被挤出可视区。改成自适应后砍掉「#」「上报人」两个低价值列、操作列 180→120，13 列正好放下且不再有省略号。

### 5. 表格外面那圈白边

`.table-section` / `.table-card` 同时套了 `card-surface`（背景 + 边框 + 圆角 + 阴影）和内层 12~18px 的 padding，表格自己还有 `border`，视觉上就是「卡片里嵌表格」的双层白边。现在去掉外层卡片，只保留圆角和 `overflow: hidden`，表格直接铺在页面上。

### 顺带修掉的一个解析 bug

九年级成绩表的列定位用的是 `headers.findIndex(h => h.includes(n))`，`idx(['长跑'], 4)` 会先命中表头 **「长跑项目」**，把「1000米」当成绩读，`parseFloat` 得 NaN；同时 `toScoreRow` 读的是 `r.idCard`，而解析器返回的是 `r.id_card`，整行身份证变成空。结果是预检直接报 SQL 语法错误（拼出了 `IN ()`）。

修法：

- 列定位改为**先精确匹配、再模糊匹配**；
- `toScoreRow` 两种命名都兼容；
- 服务端在拼 `IN (...)` 之前先返回行级校验错误，不再拼出空列表。

`test-registration.js` 因此增加到 32 条断言（新增免考关键词 2 条、备注与项目互斥 2 条、dryRun 2 条）。

## B.16 管理员「跳过错误行、只导入正确数据」（2026-11-05 追加）

### 原来的问题

管理员导入七/八年级成绩时，只要有一行校验不通过，整个导入就被挡住了：

- `POST /submissions/preview` 一发现错误就 `return`，不返回任何差异信息；
- 前端看到 `valid: false` 就把「确认导入」整条按钮藏起来。

结果是 500 行里错 1 行，也得整批改完再传一次 —— 而错误清单其实已经导出了。

### 现在的行为

预检接口新增 `allowPartial`（**仅管理员生效**，学校账号必须整批改对）：

```js
const allowPartial = Boolean(req.body.allowPartial) && !isSchoolUser

// 出错的行整行跳过，其余行照常做差异对比
const badIndexes = new Set(errors.map(e => e.row - 2))
const validIndexes = normalized.map((_, i) => i).filter(i => !badIndexes.has(i))
const diff = await buildDiff(pool, table, validIndexes.map(i => normalized[i]), school, year)
```

返回体多了三个字段：`validIndexes`（可导入行的 0 基下标）、`validCount`、`skippedCount`。

前端在「校验结果」里多一条黄色提示：

```
以上 2 处问题涉及 2 行，这些行不会被导入。其余 2 条数据是正常的，
可以先导入，剩下的改完再传一次。
```

提交按钮变成 **「仅导入正确数据（2 条）」**，确认框也会明确写出跳过多少行：

```
即将仅导入正确数据 2 条记录，导入后将立即生效，跳过 2 行有问题的数据和 2 处错误。
```

导入时按 `validIndexes` 把出错的行整行剔除，成功提示附带 `（已跳过 2 行有问题的数据）`。

### 安全边界

- `allowPartial` 只在管理员身份下生效；学校账号传了也按「全部必须正确」处理；
- 服务端拿不到 `validIndexes` 时，前端按「整组都不可导入」处理 —— 宁可不导入，也不写坏数据；
- 出错的判定仍然完全由服务端 `validateRows` 决定，前端不参与「哪些行能过」的判断。

### 顺带修掉的两个解析 bug

做这个功能时用「没有学校/年级列」的文件测试，暴露出两个老问题：

1. **年级被猜成了分数**：`cellVal(row, colMap, 'grade', 4)` 在文件没有「年级」列时回退读第 4 列 —— 恰好是「出勤率成绩」。`"90"` 含 `9` 被判成九年级、`"85"` 含 `8` 被判成八年级，于是 `999` 这种分数被送进了九年级的校验规则里（那里根本不校验 `attendance_score`），一路放行。
2. **学校被猜成了姓名**：`cellVal(row, colMap, 'school', 0)` 回退读第 0 列，没有「学校」列时整列填的是学生姓名。

修法：**没匹配到列就留空，不再按列号硬猜**；年级交给 `detectedGrade`（按表头判断七/八年级）兜底。同时管理员导入时如果发现缺「学校」列，直接提示 `有 N 行缺少「学校」列`，不再写出空学校的数据。

### 验证

`smoke-test.js` 新增 2 条断言，共 41 条：

```
管理员预检：有错误也返回可导入行   → valid=false, validCount=1, skippedCount=1, validIndexes=[0]
学校账号不能用「只导入正确数据」    → valid=false, newCount=0
```

浏览器实测一份 4 行文件（2 行正确 + 身份证非法 1 行 + 分数 999 一行）：

```
发现 2 处问题：第 4 行 id_card、第 5 行 attendance_score
新增 (2)：实验第一中学 / 正确学生A、正确学生B
[仅导入正确数据（2 条）] → 导入成功：七年级 2 条（已跳过 2 行有问题的数据）
```

库里只有这 2 条，`123` 和 `999` 那两行没有落库。

## B.17 管理员直接导入九年级报名名单（2026-11-05 追加）

### 为什么需要

B.12 把九年级改成「学校报名 → 教育局审核」之后，名单只有学校上报这一条来源。实际情况里有两种走不通的场景：

- 学校迟迟不上报，或者干脆没上线；
- 名单本来就是教育局统一提供的（中招体育考试的报名库在教育局手里）。

所以补一条管理员侧的导入通道：**报名审核 → 导入报名名单**。

### 与学校报名的关系

用的是同一张表、同一套校验，区别只有三点：

| | 学校报名 | 管理员导入 |
| --- | --- | --- |
| 学校来源 | 账号绑定，整份名单一个学校 | 每行自带「学校」，可多校合并 |
| 初始状态 | `pending`（待审核） | `approved`（视为已审核通过） |
| 是否写成绩表 | 审核通过后才写 | 导入时立即写 |

### 实现

新增 `POST /api/registrations/admin-import`：

1. 复用 `validateRegistrationRows`（证件号、性别↔身份证、性别↔长跑、球类取值、备注与项目互斥）；
2. 额外要求**每行都有学校**，缺失直接报 `缺少学校名称（管理员导入时可以含多所学校，每行都要填）`；
3. 逐行 upsert 到 `grade_nine_registrations`，状态直接置 `approved`、`reviewed_by = admin`；
4. 调用 `writeRegistrationToTables()` 把基本信息写进 `grade_nine` 与 `admission`（成绩列留空）；
5. 命中 `status = 'scored'` 的学生（成绩已导入）整批回滚，不允许改报名信息。

顺带把「审核通过」「批量通过」里重复了两遍的写表逻辑抽成 `writeRegistrationToTables(connection, reg)` —— 原来 approve 和 batch-approve 各写了一份，加上这次就是三份，早晚会漂移。

### 前端

报名审核页头部新增 **「导入报名名单」** 按钮，弹窗里：

- 说明这是为「学校没上报 / 名单由教育局统一提供」准备的；
- 明确提示可以多校合并、每行必须填学校、备注有内容时项目列留空；
- 上传后点「导入名单」→ 二次确认（说明会直接写入两张成绩表）→ 结果提示 `已导入 3 人（新增 3，更新 0）`；
- 校验失败时把 `errors` 逐行铺成表格展示，和成绩导入的交互一致。

## B.18 报名信息带出「性别」+ 清空数据的状态回退（2026-11-09 追加）

业务方确认的完整流程是：

```

管理员导入报名信息 ──→ 同上，只是不需要审核
```

其中大部分字段在 B.12 就已经带过去了，**唯独性别没有**：两张成绩表里根本没有 `gender` 列，界面上也没有这一列。

### 改动

| 位置 | 改动 |

### 附：「下载导入模板」点了没反应

管理员在成绩导入页点「下载导入模板」（七/八年级）没有任何反应。原因是这个按钮的处理函数复用了学校端的逻辑：

```js
const level = form.gradeLevel

```

`form.gradeLevel` 是学校端那个「上报年级」下拉的值，管理员的表单里根本没有这个控件，值一直是空串 —— 于是函数在第二行就静默返回了，既不下载也不报错。

修好之后：

- 管理员（七/八年级模式）下载一份 **「七、八年级体育成绩导入模板」**，示例里同时给了七年级和八年级两行（导入时年级是逐行识别的，可以混在一个文件里）；
- 学校账号仍按所选年级出对应的模板；
- 所有模板下载都补了一条成功提示（`已生成并下载「…」` / `报名表模板已开始下载`），不再出现「点了没动静」的观感。

## B.19 侧边栏「收起」按钮点了没反应（2026-11-09 追加）

现象：点左上角那个 `‹` 按钮，左侧导航栏不收起。

排查过程：

1. 元素有原生 click 事件（自己挂一个 capture 监听能收到）；
2. 但 Vue 的处理器没执行 —— class 一直是 `sidebar`，`title` 也一直是「收起菜单」；
3. 编译产物里确实有 `onClick: W`、`W=()=>{s.value=!s}`，函数本身没问题；
4. 用 JS 直接 `btn.click()` 也一样，说明处理器没绑上。

改法：把 `@click="toggleSidebar"` 换成行内表达式 `@click="isCollapsed = !isCollapsed"`，并删掉不再使用的 `toggleSidebar`。

行内表达式的处理器是**每次渲染时新建的闭包**，不存在「首次 patch 时函数还未初始化、之后又因为引用不变而不再重新绑定」的可能；而引用型处理器一旦首次拿到 `undefined`，后续渲染传的还是同一个引用，Vue 的 props diff 会认为没变化，监听器就永远补不上。

验证：展开 232px ↔ 收起 66px 双向切换正常，收起后只剩图标，`title` 同步变成「展开菜单」。

> 排查时还发现一个容易踩的坑：浏览器可能整页使用缓存的旧 `index.html`，导致加载的是上一次构建的 chunk（文件名带 hash，和新构建对不上）。遇到「改了没生效」先用带随机参数的 URL 强刷一次。

## B.20 遗留与建议

1. **`--el-color-primary` 在暗色模式下由 App.vue 覆盖**，但 Element Plus 的组件样式是按需分块加载的，未来若新增组件请确认其暗色表现。
2. **学校名仍是自由文本**（`school VARCHAR(200)`），当前靠「改名级联更新」保证一致性；数据量继续增长后建议改为 `school_id` 外键。
3. **模糊搜索 `LIKE '%kw%'` 无法走索引**，数据量到百万级时建议引入全文索引或 Elasticsearch。
4. **Excel 解析仍在主线程**，十万行级别会卡顿；建议后续移入 Web Worker（已在报告第 6 节列出）。
5. **生产部署前**务必按 `docs/部署说明.md` 第八节修改 `JWT_SECRET`、`NODE_ENV`、`CORS_ORIGINS`。
6. **报名名单与成绩表之间没有外键**，靠 `identity_id` 关联。删除报名名单不会级联删除成绩表里的记录——这是刻意的（成绩是正式数据，名单是可追溯的上报记录），但做「撤销审核」功能时需要显式处理两张表的对应行。
7. **`grade_nine_registrations.raw` 会随名单一起增长**，若单校报名动辄上千行、且长期保留多届，建议定期归档到历史表。
8. **考务编排模块**可直接消费 `grade_nine_registrations`：`raw` 保留原始列、`long_run_event`/`ball_event` 已归一化、`school`/`graduation_year` 有索引，按学校分考场时无需再解析 Excel。
